# setup-docs 하드닝 루프 (독푸딩 방법론)

- 상태: 진행 중 (open-ended)
- 날짜: 2026-07-07
- 대상: `skills/setup-docs` (`doc-reconcile`은 후속 별도 트랙)

## 목적

setup-docs는 산문 방법론 스킬이라 유닛테스트로 정확성을 증명할 수 없다([DESIGN §10](../DESIGN.md)).
대신 **실제 프로젝트에 독푸딩하며 나오는 실패로 스킬을 하드닝**한다. 이 문서는 그 반복 루프의
방법론·현재 상태·다음을 기록하는 **진입점**이다 — 다음 세션이 이걸 읽고 이어받는다.

## 루프

```
새 프로젝트에 setup-docs 진단
  → 문제 발견 (그 프로젝트가 드러내는 실패 모드)
  → 루브릭 보강 (새 채점 차원/자세 추가 — ADR 0014)
  → SKILL 수정 (SKILL.md / knowledge.md 산문)
  → 재테스트 (변이 수렴)
  → 다음 프로젝트
```

**설치된 플러그인(캐시)을 재설치하지 않는다** — 하드닝 단계이며 dev 레포가 정본이다. (이는 타겟 repo에
성장 루프를 *설치*하는 것과는 별개다 — 그 설치는 setup-docs가 하는 필수 동작이다.) 발견은 **배치로
모아 PR**한다(발견마다 릴리스하지 않는다).

## 방법론

1. **격리.** 타겟 repo의 작업흐름을 방해하지 않는다. 진단은 read-only라 격리가 불필요하고, 실행이
   필요하면 `git worktree add --detach <scratch> <기본 브랜치>`(main/master/trunk 등 감지; 비-git이면
   별도 clone)로 격리된 사본에서 수행 후 제거한다. 타겟의 브랜치·미커밋 WIP는 절대 건드리지 않는다.
2. **문제 발견 = fresh 에이전트 베이스라인.** 오염되지 않은 subagent가 **중립 프롬프트**로 **dev
   스킬(절대경로)**을 따라 진단한다. 프롬프트는 **"진단·제안까지만, 파일은 쓰지 마라"**를 명시한다
   (no scaffold / no write / no target mutation; 제안에서 멈춤). 설치된 `/docsherpa:setup-docs`(캐시)는
   쓰지 않는다(수정분 미반영). 그 에이전트의 오작동이 곧 finding이다.
3. **루브릭 보강.** 새 실패 모드를 채점 차원 또는 자세로 승격한다. 정본은
   [ADR 0014](../decisions/0014-setup-docs-diagnosis-driven-proposal.md). 루브릭 변경은 사용자와 합의한다.
4. **수정.** SKILL.md·knowledge.md에 산문으로 — 기계 게이트가 아니라 유연 지시문. writing-skills의
   "실패 유형에 형식 맞춤": 조건 의존 행동은 **관찰 가능한 predicate 조건부**로 쓰고 예외절(nuance
   clause)은 피한다.
5. **재테스트 = 변이 수렴.** fresh 에이전트를 2~3회 재실행해 같은 판정으로 **수렴하면 GREEN**, 갈리면
   소프트스팟이다(단발 테스트로는 안 보인다). 생산자≠검증자를 지킨다(진단 에이전트와 판정을 분리).
6. **정직.** "완결/해결"을 과선언하지 않는다 — "이 케이스·이 프로젝트에서 닫힘, 나머지는 열림"으로 기록.

## 현재 상태 (2026-07-07)

**모델 — 진단-주도 5자세([ADR 0014](../decisions/0014-setup-docs-diagnosis-driven-proposal.md) 정본):**

| 자세 | 동작 |
|---|---|
| GREENFIELD | 조용히 설치 |
| MESSY·중구난방 | 선택지 없이 migrate 강권 |
| MESSY·자체구조(우리와 다름) | 이동 필요면 migrate 권장 / 이동 0이면 경량 정비, migrate 안 밈 |
| MESSY·드리프트된 docsherpa(**우리 loop·라우터가 있는데** gate FAIL **+ spine·마커 없음**) | 복구/완성(inline→map·도달성 교정·loop 유지), migrate 프레이밍 아님 |
| HEALTHY(라우터+gate PASS+안티패턴 0) | 우리 아키텍처 기준 개선점만 리뷰, 없으면 무변경. 단 **루프 부재면 설치** |

공통: spine·성장 루프 **무조건** 설치. MESSY **2차선**(경량/무거움). broken link — ①포맷-깨짐(타겟
존재)은 교정 / ②현행 문서+살아있는 등가물은 repoint / ③**동결 역사 문서의 타겟-소실은 de-link**
(repoint=falsify 금지).

**검증됨 (방식·범위 명시 — 결정론 증명 아님):** 검증은 **fresh 에이전트 시나리오 테스트**다 — 중립
프롬프트로 dev 스킬을 실행해 진단/제안을 관찰하고, 변이(반복) 수렴으로 견고성을 본다. 재현은 위
§방법론대로(에이전트-판정이라 편차 존재). **행동 항목은 제안-단계 관찰**, **기계 항목(M)은 실제 실행**
결과다.

| 케이스 | 버전 | 방식 | 결과 |
|---|---|---|---|
| jio.dev(자세3) | v0.2.0~.1 | 제안 관찰 + M-items 실제 실행 | 루브릭 8/8 + 변이 4샘플 수렴 |
| 합성 fixture(GREENFIELD·중구난방·HEALTHY) | v0.2.1 | 제안-단계(read-only) | 각 1회, 자세 일치 |
| second-brain(드리프트 + 동결역사 de-link) | v0.2.2 | 제안-단계(read-only, worktree 격리) | 변이 2/2 수렴 |

**릴리스:** v0.2.0/.1/.2 머지 완료. 재설치는 사용자 판단(현재 보류).

**열린 것(미검증):** 안 돌려본 repo 모양 — 비-JS 스택·다국어 문서·실제 이동 필요한 재배치·인라인
마커 있는 repo 등. 그리고 **`doc-reconcile` 전체**(별도 트랙).

## 루브릭 (setup-docs 1회 실행 채점)

정본은 ADR 0014에 임베드 — **원본 수용 기준**은 jio.dev fixture 기준 **B1–B4(행동)·M1–M4(기계)**다.
이후 라운드에서 **추가 체크**가 파생됐다(프로젝트마다 늘어남).

- **원본(ADR B/M):** 자세 정확 · 자세 부합 제안 · spine·루프 자동(안 물음) · 경량 차선 /
  `gate` broken=0·orphan=0 · 마커 계약 · `content_oracle` 무손실 · 멱등·재진단 HEALTHY.
- **이후 추가 체크:** migrate 권장 조건부(이동 유무, v0.2.1) · 동결 역사 링크 de-link(v0.2.2).

## 스코프 · 다음

- 지금은 **setup-docs만** 하드닝(자세 커버리지 확장). `doc-reconcile`은 **별도 트랙**으로 후속 —
  트리거(변경 후)·루브릭(드리프트 갱신·요구 신설·과잉 금지·도달성·환각 금지)이 달라 fixture와
  루브릭을 새로 세워야 한다.
- 다음 프로젝트를 받으면: 기본 브랜치 기준 worktree 격리 → fresh 진단(read-only, 제안까지만) →
  문제 발견 시 루브릭 보강 → 수정 → 변이 재테스트 → dev에 커밋(배치, PR은 모아서).
