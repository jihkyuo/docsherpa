# parity 실험 돌리기 — doc-reconcile이 정말 판정을 잘하는지 재는 법

> **왜 있나.** [DESIGN.md](../DESIGN.md) §10.3이 약속한 behavioral fixture다. 산문 방법론은
> 유닛테스트할 수 없지만 **행동은 잴 수 있다.** 루프의 산문을 고칠 때마다 좋아졌는지 나빠졌는지
> 여기서 확인한다. 안 재고 고치면 추측이 된다 —
> [ADR 0021](../decisions/0021-parity-experiment-control-group.md).

기계(아레나 빌더·채점기)는 `skills/doc-reconcile/parity/`에 있고, **시나리오는 사용자 레포에 산다**
(플러그인 정본은 도메인 리터럴 0). 어떤 레포든 자기 git 히스토리가 자기 문서 루프의 회귀 테스트가 된다.

---

## 1. 정답지가 될 커밋을 찾는다

가장 좋은 재료는 **코드가 착륙한 뒤 문서만 정리한 커밋**이다. 그 부모 트리가 곧 "코드는 새것,
문서는 낡음" 상태 — 시험 문제 그 자체다.

```bash
git log --all --grep='Docs-Impact' --oneline      # 루프가 남긴 자기 기록
git log --all --oneline --grep='docs(reconcile)'  # 문서만 정리한 커밋
```

`Docs-Impact:` 트레일러는 **판정을 산문으로** 담고 있어 특히 값지다. 무엇을 고쳤는지뿐 아니라
**무엇을 일부러 안 고쳤는지**가 적혀 있다. 부정 판정이야말로 가장 귀한 라벨이다 — 루프의 진짜
실패 모드는 "못 찾는 것"이 아니라 "안 건드려도 될 걸 건드리는 것"이기 때문이다.

## 2. 시나리오 JSON을 쓴다

```json
{
  "id": "<짧은 이름>",
  "commit": "<sha>",
  "note": "<정답지 근거 — Docs-Impact 원문·판단 메모>",
  "ground_truth": {
    "update":   ["docs/A.md", "docs/decisions/0007-x.md"],
    "create":   [],
    "no_touch": ["docs/B.md"]
  }
}
```

**⚠️ `no_touch`는 파일 *전체*가 여전히 사실일 때만 넣는다.** 한 문서 안에 "여전히 사실인 주장"과
"이번 변경이 거짓으로 만든 주장"이 섞여 있으면 그 문서는 `no_touch`가 **아니다.** 넣으면 원본
루프의 맹점을 정답으로 박제하게 된다. (첫 실측에서 실제로 이 함정을 밟았다 — 두 팔 모두 원본이
놓친 stale 주장을 같은 파일에서 찾아냈는데, 채점기가 그걸 "보존 위반"으로 셌다.)

`validate_scenario()`는 `no_touch ∩ update ≠ ∅` 같은 **스펙 자기모순만** 잡는다. 위 의미 오류는
자동으로 못 잡는다 — 사람이 봐야 한다.

**정답지는 상한이 아니라 하한이다.** 그때의 사람+AI가 한 일일 뿐 완벽한 답이 아니다. 그래서
`extra_update`는 감점하지 않고 표시만 한다.

## 3. 아레나를 짓는다 (대조군)

```bash
# 코드+문서 혼합 커밋
python3 skills/doc-reconcile/parity/arena.py --repo <소스> --commit <sha> --out <작업 디렉터리>

# 문서-정리 전용 커밋(가장 좋은 재료) — 코드는 그 전에 착륙했다
python3 skills/doc-reconcile/parity/arena.py --repo <소스> --commit <sha> \
  --code-base <코드 작업 직전 rev> --out <작업 디렉터리>
```

산출: `control/`(부모 트리) · `code-change.diff`(비-문서 변경) · `code-change.log`.

**에이전트가 보는 트리는 언제나 부모다** — 코드는 새것, 문서는 낡음. 다만 *"방금 무슨 코드를
바꿨나"*는 커밋 유형에 따라 다르다. 문서-정리 전용 커밋은 자기 diff에 코드가 **없으므로**
`--code-base`로 코드 착륙 구간(`code_base..parent`)을 지정해야 한다. 안 주면 `arena.py`가
빈 diff를 조용히 넘기지 않고 멈춘다.

**정답 누출이 이 도구의 유일한 치명 실패다. 새는 곳은 두 군데인데, 위험한 쪽은 흔히 오해된다.**

- **트리의 `.git`** — `git archive`가 애초에 히스토리를 안 담는다. 사실상 안전하다.
- **diff에 섞인 문서 변경** — **이쪽이 진짜다.** 에이전트는 diff를 읽으므로, 정리 커밋의 문서
  변경이 한 줄이라도 diff에 들어가면 정답을 그대로 본다. `arena.py`는 문서 판정을 **대소문자
  무시**로 하고(`README.MD`), `.md`뿐 아니라 `.mdx`·`.markdown`·`.rst`·`.adoc`을 기본으로 막으며,
  산출된 diff를 **다시 훑어** 문서가 하나라도 있으면 `ArenaError`로 멈춘다.
  `--doc-glob`은 기본값에 **더할 수만 있고 좁힐 수 없다** — 좁히면 정답이 새기 때문이다.

`arena.py`는 **루트 커밋**(부모 없음)과 **머지 커밋**(직전 상태가 모호)도 읽히는 오류로 거절한다.
`.gitattributes`의 `export-ignore`가 붙은 문서는 `control/`에 안 나타난다는 점만 유의하라.

## 4. 처리군을 만든다 (비교 대상이 있을 때만)

대조군 트리를 복제한 뒤, **비교하려는 루프**를 설치한다. 예를 들어 "손으로 쓴 라우터 vs
docsherpa가 생성한 라우터"를 견주려면:

1. 복제본에서 **docsherpa가 공급하겠다고 주장하는 것만** 벗긴다 — 설치본 `doc-reconcile`·prime,
   그리고 진입파일의 인덱스·라우팅 룰 섹션.
2. **보존하겠다고 주장하는 것은 남긴다** — 진입파일의 나머지 산문(철칙·컨벤션), `settings.json`,
   `docs/` 트리 전부.
3. `/docsherpa:setup-docs`를 돌린다.

이 경계가 곧 타깃 고객의 모습이다. 더 벗기면 그린필드를, 덜 벗기면 오염된 처리군을 테스트한다.

> **⚠️ 워킹트리만 벗기면 오염된다.** git 히스토리에 옛 루프가 커밋돼 있으면 진단이
> "드리프트된 docsherpa"로 흐른다. 벗긴 상태를 커밋한 뒤 아레나로 뽑아라.

## 5. 양 팔에 **똑같은** 질문을 던진다

각 아레나마다 신선한 에이전트를 띄운다. 프롬프트는 팔 사이에 한 글자도 달라선 안 된다.

- 아레나 밖(원본 레포·플러그인)을 읽지 못하게 막는다.
- 아무것도 쓰지 못하게 한다(report-only).
- 레포의 루프를 **스스로 찾아 따르게** 한다: `.claude/settings.json` → prime → `doc-reconcile`.
- 리포트에 **fenced json 판정을 정확히 하나** 요구한다. 키는 `update`·`create`·`no_touch`,
  값은 **repo-상대 경로**(절대경로·`./` 접두사 금지). 형식 예시를 리포트에 다시 적지 말라고
  못박는다 — 판정 블록이 둘이 되면 채점기가 **추측하지 않고 멈춘다**(그게 옳다).

에이전트가 절대경로를 내면 `score.py --root <아레나>/control`로 정규화하라. 안 그러면 정답과
매칭이 안 돼 **재현율이 조용히 0으로 깎인다** — 채점기가 이걸 감지해 멈추지만, 애초에 프롬프트에서
막는 게 낫다.

**n>1로 반복한다.** LLM은 확률적이다. 실측에서 각 팔 내부의 실행 간 변동이 팔 사이 차이보다
컸다 — n=1 결과로 구조적 결함을 단정하면 존재하지 않는 문제를 고치게 된다. 최소 3회.

## 6. 채점한다

```bash
python3 skills/doc-reconcile/parity/score.py \
  --scenario <시나리오>.json --report r1.md --report r2.md --report r3.md
```

세 축을 **따로** 잰다. 하나로 합치면 무엇이 고장났는지 알 수 없다.

| 축 | 묻는 것 | 실측 경향 |
|---|---|---|
| **탐지** | 낡은 문서를 찾았나 | 가장 약함 — 흔들린다 |
| **억제** | 필요 없는 문서를 안 만들었나 | 견고 |
| **보존** | 여전히 사실인 문서를 안 건드렸나 | 견고 |

루프의 체감 가치는 **탐지가 아니라 억제·보존**에서 온다. 탐지가 흔들려도 사용자는 잘 모르지만,
억제·보존이 무너지면 문서가 즉시 오염된다. 개선 작업의 우선순위를 여기서 읽어라.

## 7. 결과로 결정한다

- 처리군이 대조군보다 **유의하게** 나쁘지 않으면 → 가설은 반증되지 않았다.
- 두 팔 다 특정 축이 낮으면 → 그건 **루프 자체의 문제**지 이식의 문제가 아니다. 산문을 고쳐라.
- 축을 하나 고친 뒤 **같은 시나리오로 재측정**한다. 오르면 채택, 안 오르면 폐기.

**고치고 나서 재는 게 아니라, 재고 나서 고친다.** 순서가 뒤집히면 "좋아진 것 같다"로 끝난다.
