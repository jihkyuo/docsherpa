# doc-reconcile

## 목적

방금 한 코드·정책·구조 변경이 문서에 남긴 흔적을 정리한다. **두 방향 모두**:

- **갱신**: 변경으로 현실과 어긋난 기존 문서를 고친다.
- **신설**: 변경에 담긴 결정을 AGENTS.md 문서 아키텍처가 요구하는데 문서가 없으면 만든다
  (ADR·트레이드오프·how-to·spec). 이게 자주 빠지는 절반이다.

**판단 엔진은 이 스킬이 아니라 라우터가 가리키는 마커 섹션이다.** "어떤 문서가 어디로·언제"의 정본은
라우팅 마커(`<!-- docsherpa:routing -->`)·인덱스 마커(`<!-- docsherpa:index -->`)가 붙은 섹션 — 진입파일
(AGENTS.md) 인라인이거나, 진입파일이 `<!-- docsherpa:map -->` 링크로 가리키는 **맵 문서**(`docs/_map.md`) —
그리고 `docs/decisions/README.md`다. 헤딩이 번역·재작성되거나 위치가 옮겨져도 마커로 찾는다. 이 스킬은 그걸
*빠짐없이·일관되게* 돌리는 절차와, baseline이 자주 새는 지점만 강제한다. **문서 taxonomy를
여기 복제하지 마라** — 라우터를 읽고 인용하라(single source).

## 출력 형태 (먼저 읽어라)

기본은 **짧은 제안**이다. 거대한 감사 리포트를 앞에 쏟아내지 마라.

1. 먼저 요약 제안: 갱신할 stale 문서 N곳 + 신설 M건을 **각 한 줄**로 요약하고 "갱신할까요?" 묻는다.
2. 사용자가 승낙하면 그때 실제 편집하고, 각 변경에만 근거(diff·모순·결정)를 붙인다.

아래 절차(§1~§6)는 그 **편집 단계의 내부 방법론**이다 — 절차 전체나 긴 표를 사용자에게 출력하는 게 아니다.

## 절차

### 0. 설치본 refresh (플러그인 실행 시만 — 결정론)

`/docsherpa:doc-reconcile`로 실행돼 plugin_root를 확보할 수 있을 때, 시작 전 설치본 갱신을 시도한다:
`python3 <plugin>/skills/setup-docs/scripts/refresh.py`의 `refresh_loop(repo_root, plugin_root)`를
호출(또는 동등 조회). 이 기계는 다운그레이드를 차단하고, 사용자가 설치본을 직접 고쳤으면 안 덮으며
(stuck), provenance 실패(설치본만 있는 repo) 시 조용히 no-op한다. **커밋하지 않는다** — 결과는
아래 끝 요약으로 사용자에게 알린다. plugin_root가 없으면(설치본에서 실행) 이 단계는 건너뛴다.

### 1. 변경 수집 (결정론적)

- `git diff --name-status` + `git diff` — **staged·unstaged 둘 다**. 세션 작업이 stage 안 됐을 수 있다.
- `git status`로 **미커밋·untracked 신규 파일**까지 잡아라. 새 prod 모듈은 코드맵에서 고아가 되기 쉽다.
- 추가/삭제된 **리터럴·상수명·명령명·사용자 용어**를 뽑아 문서 검색어로 쓴다(`grep -r docs/`).

### 2. 두 방향 판정 — 라우터 마커 섹션으로

각 변경 surface마다 세 질문을 던진다:

- 이 변경으로 어긋난 **기존 문서**가 있나? → 갱신 후보
- 라우팅 마커(`<!-- docsherpa:routing -->`) 섹션(진입파일 또는 맵 문서)이 **새 문서**를 요구하나? (구조적 결정 → ADR + `decisions/README.md`
  로그 한 줄 / 제품 요구(왜 만드나·누구) → product/(PRD) / 작업 가이드 → how-to / 기능 스펙 → specs …) 요구하는데 없으면 → 신설 후보
- 평면 `docs/`에 **같은 주제·co-change 문서가 ≥2개** 실제로 뭉쳐 있나?(단발 우연 말고 판단) → 룰#4대로
  `docs/<topic>/` **승격을 비블로킹 제안**(리드 문서=인덱스). ⚠️ **doc-reconcile은 파일을 옮기지 않는다**
  — 이동=내용 위험이라 실제 이동·링크 리라이트는 setup-docs 폴더 승격(MESSY two-oracle, content_oracle-safe·
  승인)에 맡긴다. 안 하면 콘텐츠가 평면으로만 자라고 절대 안 뭉친다.

**대상 문서는 고정 목록이 아니다.** 이 변경이 실제로 무엇을 건드리는지 매번 새로 물어라.
아래는 "자주 새는 앵커"일 뿐 — **바닥이지 천장이 아니다. 이것만 보지 마라**. 어떤 앵커의 대상
문서가 이 프로젝트에 없으면 그 앵커는 조용히 건너뛴다(빈 자리표시를 남기지 말 것):

<!-- docsherpa:anchors:start — setup-docs가 스캐폴드 시 이 블록을 target의 실재 문서 경로로 특화한다(§7.5). 대응 문서 없으면 일반형 유지. -->
- 상수/설정 파일 변경 → 그 수치를 담은 스펙 문서(있으면)의 해당 값
- provider/model/tier 등 구조 상수·타입 변경 → 관련 ADR **+ 근거가 뒤집힌 기존 ADR**
- 새 prod 모듈 → 코드맵 문서(있으면)의 행 (+ 해당되면 라우터의 derived 목록)
<!-- docsherpa:anchors:end -->
- **이번 세션에 어렵게 진단·복구한 문제**(반복 가능 + 비쌈 + 예방/재현 절차 있음) → `how-to/`에
  troubleshooting **절차**로 졸업. ⚠️ 다른 앵커는 "무엇이 *바뀌었나*"(diff)가 트리거지만 이건
  "무엇을 *배웠나*"가 트리거 — **코드 diff가 작아도(심지어 픽스가 다른 repo·다른 패키지라도) 발동**한다.
  그래서 diff-스캔만 하면 정확히 이게 샌다(이번 세션 트리거인 트러블슈팅을 놓침). 단 symptom→link뿐이면
  만들지 마라 — 주인 문서(한계·개념 함정)에 alias하고, 재현·진단·복구 **절차**가 있을 때만 how-to로.

**spec은 ADR을 대체하지 않는다 — 닫아야 할 합리화.** design spec(`specs/`)은 "무엇을·어떻게"
(라우팅 룰 #3), ADR(`decisions/`)은 "왜 이걸 골랐나 + 대안 + 결과"(룰 #1). 둘은 **다른 도달성
트리**에 산다 — spec은 인덱스에 없으면 orphan이고, "왜"는 `decisions/README.md`에서 찾는다.
**구조적 결정이면 spec이 있어도 ADR(최소 stub)을 신설**하고 `decisions/README.md`에 로그 한 줄 +
spec과 상호링크하라. "spec에 근거 있으니 ADR 불필요"는 정확히 ADR 인프라를 안 쓰게 만드는 함정 —
결정 근거가 decisions 로그에서 **도달 가능**해야 완료다. (spec이 이미 orphan이면 이 신설이 그걸 잇는다.)
마찬가지로 **PRD(왜 만드나·누구·성공기준)는 ADR(왜 이 기술선택)을 대체하지 않는다** — 구조적 결정이면
PRD가 있어도 ADR을 병렬 신설·상호링크하라.

### 3. 자주 새는 지점 — 강제 체크 (baseline이 비일관적이던 곳)

- **모든 상태/lifecycle 주장을 훑어라 — 이 작업을 *유발한* spec/plan 자신의 상태까지.**
  예: design spec이 "구현 대기"인데 이미 구현됨 → "구현됨"으로. ROADMAP의 "미구현" 항목이
  이번에 구현됐으면 → 갱신. (상태 표기는 다음 세션이 신뢰하는 대상이다.)
- **네가 편집하는 줄의 숫자·개수·리터럴은 코드/설정에 대조하라.** "논리 불변"이라
  가정하고 지나치지 마라 — 이미 만지는 줄에 검증 안 된 falsehood를 남기지 마라.
  예: 개념 문서가 "항목 3개"라 쓰는데 코드엔 4개면, 편집하는 줄에서 그 수를 코드에 맞춰 고쳐라.
- **코드 주석의 stale 표현은 스코프를 명시적으로 결정하라** — in이면 고치고, out이면 flag만.
  조용히 애매하게 넘기지 마라.

### 4. anti-hallucination (drift 지어내기 방지)

모든 수정·신설은 **그걸 강제한 diff·문서 모순·결정을 인용**하라. 근거를 못 대면 손대지 마라.
어떤 문서도 바뀔 필요가 없는 게 맞다면 → 커밋 메시지에 `Docs-Impact: none - <구체적 이유>`.

### 5. canonical 방향

코드·config가 behavior/수치의 진실. **문서를 코드에 맞춘다(반대 아님).** accepted ADR 본문은
재작성하지 말고, 근거가 사실과 반대가 됐으면 supersession/상태만 갱신한다.

### 6. 도달성 closeout

새 문서는 반드시 인덱스 마커(`<!-- docsherpa:index -->`) 섹션/라우터에 **한 줄 추가**한다(안 하면 고아 — 에이전트가 도달 못 함).
**그리고 이 변경이 근거로 기대는 기존 문서(spec 등)가 이미 orphan이면 그것도 인덱싱하라** —
"새 문서 0이니 도달성 N/A"로 넘기지 마라. 변경의 "왜"가 어디선가 도달 가능해야 한다.
끝에 broken=0 · orphan=0 확인.

### 7. 끝 요약 (refresh 결과 포함)

실행 끝에 사용자에게 요약한다: 📝갱신 N · 🆕신설 M · ⚙️refresh(했으면 "설치본 vX→vY 갱신됨 —
`git diff .claude/` 확인 후 커밋" / stuck이면 "설치본이 로컬 편집돼 자동갱신 skip — 수동 확인 필요").
무변경이면 `Docs-Impact: none`.

## 손대지 말 것 (자주 오버리치하는 곳)

- **역사를 동결한 문서**: 과거 `plans/`·`specs/`의 옛 표현, accepted ADR 본문(근거 반전만 갱신).
- **provider가 아닌 것**: 커밋 트레일러의 `Co-Authored-By`(=코딩 도구지 LLM 백엔드 아님),
  데이터 엔티티 예시, 원본 아키텍처 인용(예: 원본이 명시한 특정 모델명).
- **pre-existing 버그**: 이번 변경이 만든 게 아니면 **flag만, 고치지 마라**. 단 §3처럼 네가 이미
  편집하는 줄 위의 falsehood는 예외(이미 만지는 줄이니 고친다).

## Common Mistakes

- taxonomy를 스킬에 복제 → AGENTS.md와 이중관리. 라우터를 읽고 인용하라.
- 진입 문서만 보고 "전부 고쳐짐" 선언 → 산문 속 잔재(옛 provider·모델명)와 근거 반전 ADR 놓침.
- 미커밋·untracked 신규 파일 무시 → 코드맵 고아.
- 편집하는 줄의 숫자를 검증 없이 유지 → falsehood 전파(3 vs 4).
- 새 ADR만 만들고 `decisions/README.md` 로그·인덱스 등록 누락 → 도달 불가.
- "design spec 있으니 ADR 불필요" → spec(무엇)과 ADR(왜)은 다른 도달성 트리. 구조결정은 ADR 신설.
